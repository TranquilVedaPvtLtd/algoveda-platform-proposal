Block 5 · Risk and Decision Criteria

The risks we have planned for, and how to evaluate this.

Sir, these are the risks you raised on our call, plus the universal ones. Each one has a single named mitigation.

5a. Risks we have planned for

Kite WebSocket disconnects mid-market
Mitigation: Reconnect with exponential backoff, full position and order reconcile via REST before any new order is permitted, idempotent intent queue gated on last-known-good snapshot.
Daily token refresh fails for a configuration
Mitigation: Bhopesh's daily checklist runs by 8:30 IST; Telegram alert fires within 60 seconds of any failed refresh; we are on the same alert thread.
Quantity multiplier fat-finger
Mitigation: Per-configuration hard caps enforced server-side. Multiplier values above 1.5x trigger a confirmation modal. Above 2x is disabled by default and unlocked only via a separate setting.
Static IP changes more than once a week (Kite limit)
Mitigation: Mumbai VPS with elastic IP held at network layer; we own the IP, not the compute layer. IP outlives any single instance.
Strategy parameter edit triggers a runaway trade
Mitigation: Param changes staged with a 30-second confirmation cool-off; bounds-checked against last 30 days of tick data; logged to an append-only audit trail.
If the TranquilVeda team becomes unavailable
Mitigation: Full codebase, runbook, and credentials vault handed over at go-live. You and Bhopesh can operate the platform independently. No code escrow needed.
If the AI/API providers deprecate a model or endpoint
Mitigation: No AI in the order path. Pure deterministic execution against Kite Connect. Only model-side risk is Zerodha changing the API itself, in which case we patch under the monthly retainer.
If results miss expectations by month 3
Mitigation: Trading outcomes are not in our scope; what we guarantee is fidelity of execution (signal to order placement under 2 seconds, audit trail completeness, uptime during market hours).
